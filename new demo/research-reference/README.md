# Version Context and Control Construction in Machine Learning Detection of Malicious Package Updates Across npm and PyPI

Code, data and results for the manuscript of the same title, submitted to *Scientific Reports*.

> Moatasem M. Draz, Kafrelsheikh University
> Submitted to *Scientific Reports* (submission 35109da0).

## What the study shows

Malicious *update* detection means catching the release in which a previously benign npm
or PyPI package is compromised. This repository builds consecutive version pairs, extracts
textual indicators from the code each update adds, and evaluates a detector under strict
package-disjoint conditions.

The central finding is that **how the benign control set is constructed determines the
reported performance**. The same model gives:

| control design | ROC-AUC |
|---|---|
| within-package (an ordinary later release of the same package) | 0.551 |
| **size-matched clean packages (primary result)** | **0.801 +/- 0.006** |
| unmatched clean packages | 0.875 |

That spread is wider than the differences usually reported between competing detectors, and
it shows the signal lives at the level of the **package**, not the individual update.
Version context contributes a small but specific signal on the primary pairs (+0.044 PR-AUC package-grouped, +0.041 random; a wrong-package predecessor scores lower still), but the paper's weight rests on the control-construction finding, not on a strong version-context claim.

## Every number is traceable

See `docs/NUMBER_TO_ARTIFACT_MAP.md`. It lists each quantity in the paper, its value, and
the exact result file and notebook that produce it. The two authoritative files are:

- `results/canonical_results.json` - the primary detector result (0.801, 0.792, operating
  points, per-ecosystem, size-only baseline), computed on the size-matched configuration.
- `results/version_context_primary_final.json` - the value of version context under both
  random and package-grouped evaluation, measured on the 360 primary malicious pairs with
  the predecessor features those pairs carry. (`results/version_context_results.json` is an
  earlier experiment on a different sample; it is marked SUPERSEDED and should not be cited.)

`revision_results_v6.json` holds the three control designs. The leakage and confounding
diagnostics of Section 6.9.2 are computed on the dataset of the *original* submission and
are regenerated by `python code/export_leakage_diagnostics.py`, which writes
`results/leakage_diagnostics.json`. `model_comparison_ci.csv` and `ablation.csv` are the
original random-CV tables, kept so the size of the correction from the first submission is
visible.

## Two feature representations

The paper reports two representations and the distinction matters when reading the code:

- the **original** representation (`data/features/features_original.csv`, 21 features:
  `after_*`, `delta_*`, entropy, AST node count) underlies Sections 6.1-6.8 of the paper,
  which are superseded;
- the **corrected** representation (`features_v6_clean.csv` / `features_v6_controls.csv`,
  60 features: `add_/rem_/net_*`, `addrate_*`, change-size, `tb_*`, `sc_*`, `ih_*`)
  underlies Section 6.9 onwards and every claim the paper makes. The abstract-syntax-tree
  feature of the original representation is not retained; the ecosystem indicator is not
  part of the corrected feature set.

The extraction for the corrected representation is the cell at the top of
`notebooks/05_sample_hygiene.ipynb`; the signal patterns for the original representation are
in `code/supply_chain_detector.py`.

## Reproducing

```
pip install -r requirements.txt
```

Notebooks 01-05 rebuild the dataset and features from the registries; 06 runs the runtime
and manual-verification add-ons; 07 produces the canonical evaluation. They are written for
Google Colab (they fetch archives from npm and PyPI at run time and cache to Drive) but run
anywhere with network access. Reading version columns as strings is required - pandas will
otherwise coerce version identifiers to floats.

## Data note and safety

The data files contain **version identifiers** of known-malicious releases for
reproducibility. They do **not** contain malicious payloads. The corresponding archives are
retrieved from the public registries at run time and are never redistributed here. The
feature definitions describe classes of suspicious behaviour that are useful for detection
without providing a recipe for evasion.

## Environment

`requirements.txt` gives the minimum versions needed to run the code. The exact
scikit-learn version used for the original canonical run was not recorded, and minor
differences in fold allocation can occur between versions, so every result file written
by the deposited scripts records the scikit-learn version that produced it. Differences
of one or two observations in a confusion matrix are expected from this and do not
indicate a different model, dataset or protocol.
